---
title: Migrating to v6
description: Migrate feature imports to independently versioned plugin packages.
---

Use `pnpm dlx @btst/codegen@6.0.0 init` for the stable v6 installation set.
The npm `next` channel now tests the [6.2 beta installation set](/release-6-2).
The version table below records the initial v6 migration; use the beta guide for
current package versions, new plugins, and additional database migrations.

BTST v6 keeps the shared runtime in `@btst/stack`. Install each selected plugin
package alongside core. Plugin package versions describe their own backend and
client contract; they do not need to match the core version.

The initial tested set uses Core `6.0.0` and all 19 independently versioned
plugin packages at `1.0.0`. Install the features your application selects and their
documented code dependencies. Runtime registration is separate: for example,
Job Board uses Form Builder code without automatically registering its routes.
The CLI selects the tested package and adapter versions, adds required runtime
registrations, and wires Blog–Newsletter behavior only when both are selected.

Plugins support Core `>=6.0.0 <7.0.0`. At the first stable rollout the minimum and latest
supported Core versions are both `6.0.0`. The optional companion selection uses
`@btst/better-auth-ui@3.0.3` for Core v6.

The [complete v5.2.0 import map](https://github.com/better-stack-ai/better-stack/blob/main/scripts/packed-consumer/v5-import-mapping.json)
records every one of the 157 original exports, including retained Core contracts,
CSS and module-specific declaration surfaces. Feature imports move to their
owners; generic Core plugin-authoring imports remain in Core. In particular,
old `@btst/stack/ui/css` moves to the separate `@btst/components/ui/css` theme,
while Markdown CSS stays at `@btst/components/markdown/css`.

Packages and their exact local candidate artifacts can be checked before npm
provisioning or first publication. Core v6 contains no legacy feature/component
facade. Existing routes, plugin IDs, permissions, query keys, serialized data
and model/table identities are preserved; this package move needs no data reset.

## Tested installation set

Use `@btst/codegen@6.0.0` with Core `6.0.0`, the 19 feature owners at `1.0.0`,
and optional `@btst/components@1.0.0`. The supported adapters are
`@btst/adapter-memory`, `@btst/adapter-prisma`, `@btst/adapter-drizzle`,
`@btst/adapter-kysely`, and `@btst/adapter-mongodb`, each at `3.0.1`.
Core uses `@btst/db@3.0.1` and `@btst/yar@1.3.2`. The scaffold pins
`lucide-react@0.475.0` to the shared UI cohort so server and browser bundles
use that tested direct dependency. Blog retains its own `^1.63.0` icon dependency.
For Vite SSR, add `lucide-react` to `ssr.noExternal` so each owner keeps its own
resolution on the server and browser; the CLI patches supported static configs.

The [package version table](https://github.com/better-stack-ai/better-stack/blob/main/packages/cli/src/utils/installation-set.ts)
and [adapter, Auth, AI and ORM metadata](https://github.com/better-stack-ai/better-stack/blob/main/packages/cli/src/utils/constants.ts)
record the complete coordinated installation set, including the exact selected
third-party versions. Install only the extras required by your selected features
and adapter. The companion's `auth` and `account` client registrations still
require an application-owned Better Auth backend; selecting it does not configure
organization, API-key, or passkey features. Form Builder and Affiliate require
an adapter with isolated transactions; the CLI rejects memory scaffolds for them.

## Vitest dependency transformation

If your Vitest configuration inlines `@btst/stack` to transform dependency CSS
or apply module mocks, add the extracted packages your tests import. For example,
AI Chat imports editor CSS and Media tests may mock a storage provider SDK:

```ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    server: {
      deps: {
        inline: ["@btst/stack", "@btst/plugin-ai-chat", "@btst/plugin-media"],
      },
    },
  },
});
```

This configuration affects the test runner; application imports still use each
package's public entries.

## Independent releases

Use `pnpm changeset` to describe a change to the packages it affects, then inspect
`pnpm changeset status` before versioning. There are no fixed or linked release
groups. A change to AI Chat does not require a release of an unchanged unrelated
plugin. A CLI release exposes a tested installation set through its exact package
specifications, including the existing adapter and companion dependency pins.
