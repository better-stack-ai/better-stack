Analytics stores page views and custom events in your BTST database. The client
sends first-party beacons without adding a third-party script or setting cookies.
The dashboard shows traffic, referrers, custom events, and recent visitors.

## Registration

Install `@btst/plugin-analytics@1.1.0` alongside `@btst/stack@6.0.0`. Analytics
uses the shared Core runtime without other plugin packages or the optional
standalone components package. Import its stylesheet for the dashboard.

Follow the [framework installation guide](/installation), then register both
halves under the canonical `analytics` key:

```ts title="lib/stack.ts"
import { createBackendStack } from "@btst/stack/api"
import { analyticsBackendPlugin } from "@btst/plugin-analytics/api"

export const myStack = createBackendStack({
  basePath: "/api/data",
  adapter,
  auth: serverAuth,
  plugins: {
    analytics: analyticsBackendPlugin({
      retentionDays: 90,
      sessionSecret: process.env.ANALYTICS_SESSION_SECRET,
    }),
  },
})
```

Use a persistent database adapter in production. Set `ANALYTICS_SESSION_SECRET`
to a private random value of at least 16 characters shared by every server instance so anonymous session
hashes are consistent across instances.

```tsx title="lib/stack-client.tsx"
import { createClientStack } from "@btst/stack/client"
import { analyticsClientPlugin } from "@btst/plugin-analytics/client"

export function getStackClient(queryClient, origin: string) {
  return createClientStack({
    api: { baseURL: origin, basePath: "/api/data" },
    site: { baseURL: origin, basePath: "/pages" },
    queryClient,
    plugins: { analytics: analyticsClientPlugin() },
  })
}
```

```css title="globals.css"
@import "@btst/plugin-analytics/css";
```

Mount the resolved stack in `StackProvider` with your framework router and client
auth adapter. Shared API, site, and query client configuration belongs on the
stack, not in analytics options.

## Authorization

Register `analyticsPermissions` from
`@btst/plugin-analytics/permissions` with your application's shared
authorization contract. Allow anonymous ingestion separately from dashboard
access. For an identity with a `role` field, these rules restrict reads, exports,
and retention cleanup to administrators:

```ts
permissions: [analyticsPermissions] as const,
rules: ({ analytics }) => [
  analytics.events.ingest.allow(),
  analytics.dashboard.read.when(({ identity }) => identity?.role === "admin"),
  analytics.dashboard.export.when(({ identity }) => identity?.role === "admin"),
  analytics.events.cleanup.when(({ identity }) => identity?.role === "admin"),
],
```

The dashboard uses the same authorization policy as the backend. It remains a
dynamic route; do not statically generate protected analytics data. With Next.js,
keep it in a request-rendered layout with `dynamic = "force-dynamic"`.

## Automatic page views

The analytics client plugin subscribes to `onRouteRender`. When a BTST route
renders in the browser, it sends the path to the ingestion API. Query strings
and fragments are removed. Server rendering does not send a page view.

Set `analyticsClientPlugin({ tracking: false })` to disable automatic tracking.
Routes outside BTST need an explicit tracker call after their router navigates.

## Custom events

After the analytics plugin has registered its browser runtime, use `track`:

```ts
import { track } from "@btst/plugin-analytics/client"

await track("signup_completed", { plan: "pro" })
```

For pages outside BTST or an explicit destination, create a tracker:

```ts
import { createAnalyticsTracker } from "@btst/plugin-analytics/client"

const analytics = createAnalyticsTracker({ apiBasePath: "/api/data" })
await analytics.track("button_clicked", { label: "Request demo" })
```

The plugin reuses public `endpoints.analytics.api.browserHeaders` for collection.
Standalone trackers accept `headers` for the same purpose. Custom headers use
keepalive Fetch instead of a beacon; requests retain the JSON content type.

Properties accept a flat object of strings, finite numbers, booleans, and null.
Do not send names, email addresses, account identifiers, or other personal data.
The server bounds the event name, path, and properties before accepting a record.

## Dashboard

With `site.basePath: "/pages"`, open `/pages/analytics`. Choose Today, 7 days,
30 days, or a custom UTC date range. The dashboard includes:

- Unique anonymous visitors, page views, bounce rate, and session duration.
- A daily traffic chart and top pages with trend sparklines.
- Top external referrers and custom event counts.
- A polling count of recently active visitors.
- Export CSV for the selected range.

![Analytics dashboard with traffic and top-page tables](/images/analytics-dashboard.png)

The image shows local demonstration traffic. Production dashboards display
events ingested by your application.

## Aggregation API

Use request-bound operations when serving application requests. They run the
same authorization and validation as HTTP endpoints:

```ts
const analytics = myStack.forRequest(request).operations.analytics
const stats = await analytics.getDashboardStats({ range: "30d" })
const pages = await analytics.getTopPages({ range: "7d", limit: 10 })
const referrers = await analytics.getTopReferrers({ range: "7d" })

// Embed a view count using an authorized server-side query.
const post = await analytics.getDashboardStats({
  range: "30d",
  path: "/blog/introducing-our-product",
})
console.log(post.pageViews)
```

Trusted server jobs can call `myStack.trusted.analytics`. Keep trusted operations
on the server; do not expose their output without applying your own access policy.
Date filters accept `range`, `start`, `end`, `path`, and `limit`. Custom ranges
require both dates and span at most 366 days; a date-only end includes that UTC day.

| Method and path, under `api.basePath` | Operation |
| --- | --- |
| `POST /analytics/pageviews` | `recordPageView` |
| `POST /analytics/events` | `recordEvent` |
| `GET /analytics/dashboard` | `getDashboardStats` |
| `GET /analytics/pages` | `getTopPages` |
| `GET /analytics/referrers` | `getTopReferrers` |
| `GET /analytics/events` | `getTopEvents` |
| `GET /analytics/realtime` | `getRealtimeVisitors` |
| `GET /analytics/export` | `exportEvents` |
| `POST /analytics/retention` | `cleanupExpiredEvents` |

## Privacy and measurement

The tracker keeps its anonymous session identifier in memory rather than browser
storage. Reloading or opening another tab can start a new session, so unique
visitor counts are estimates rather than a count of distinct people. The server
hashes session identifiers with a daily salt before storage and never stores raw IP
addresses. Daily rotation also separates the same session across UTC days.
Referrer analytics retain the external host rather than sensitive URL details.
Recognized bots are filtered by user agent; this reduces crawler traffic but
does not authenticate human visitors.

Bounce rate measures sessions with one page view. Session duration measures the
time between the first and last recorded page view, averaged across sessions
including bounces as zero. Visits split after 30 minutes of page-view inactivity.
Custom events do not change bounce rate or session duration. Leaving a page open
does not produce a heartbeat. Date filters and
retention can shorten the activity visible to these calculations.

Custom properties and page paths are application-controlled. Avoid putting
personal data in paths or event properties. Your application owns its event
properties and privacy policy.

## Retention and hooks

`retentionDays` defaults to 90. Schedule cleanup to remove expired records even
when your site receives no traffic:

```ts
await myStack.trusted.analytics.cleanupExpiredEvents({})
```

Use lifecycle hooks for application-specific filtering and observation. Hooks run
inside the validated, authorized ingestion operation; access control belongs in
the shared authorization rules.

```ts
analyticsBackendPlugin({
  hooks: {
    onBeforeIngest: async (event) => {
      if (event.path.startsWith("/internal")) throw new Error("Excluded path")
    },
    onAfterIngest: async (event) => {
      console.log("Analytics event recorded", event.path)
    },
  },
})
```

## Lifecycle bridges

Analytics 1.1 adds typed helpers for Feature Flags, Form Builder, Newsletter,
Calendar, Ecommerce, and School. The source plugins remain independently
installable. Analytics imports none of those packages.

```ts
import { createAnalyticsServerHooks } from "@btst/plugin-analytics/api"

const analyticsHooks = createAnalyticsServerHooks({
  recordEvent: (event) => myStack.trusted.analytics.recordEvent(event),
  session: async ({ request }) => {
    // Resolve your application's existing consented anonymous session.
    // Return null when collection is not permitted; never use an email or user ID.
    return resolveConsentedAnonymousSession(request)
  },
})

// Inside the corresponding plugin registration:
featureFlagsBackendPlugin({ hooks: analyticsHooks.featureFlags })
formBuilderBackendPlugin({ hooks: analyticsHooks.formBuilder })
newsletterBackendPlugin({ ...newsletterOptions, hooks: analyticsHooks.newsletter })
calendarBackendPlugin({ hooks: analyticsHooks.calendar })
ecommerceBackendPlugin({ ...checkoutOptions, hooks: analyticsHooks.ecommerce })
schoolBackendPlugin({ hooks: analyticsHooks.school })
```

The server resolver must return an opaque session ID of 16–128 characters or
`null`. Use the same consented anonymous session for flag exposure and conversion
events to correlate them. Analytics validates events, hashes sessions daily, runs
ingestion hooks, and applies retention through `trusted.analytics.recordEvent`.
The helper skips requests with `DNT: 1` or `Sec-GPC: 1` before calling the resolver.

Calendar and School lifecycle hooks have no HTTP request argument. Payment
webhooks contain the provider request, not the customer's original browser
session or consent. Their correlation and consent therefore remain application
responsibilities; the helpers never reconstruct identity from user IDs, emails,
cookies, or entity IDs. Do not enable collection for request-less callbacks until
your application can resolve that consented context.

| Source callback | Event | Properties |
| --- | --- | --- |
| Feature Flags `onEvaluate` | `feature_flag_evaluated` | `flag`, boolean `result`, actual assigned `variant` or `null` |
| Form Builder `onAfterSubmission` | `form_submitted` | `formId` |
| Newsletter `onAfterSubscribe` | `newsletter_subscribed` | none; subscribed records only |
| Calendar `onAfterConfirmBooking` | `booking_confirmed` | `eventTypeId`; newly confirmed records only |
| Calendar `onAfterRescheduleBooking` | `booking_rescheduled` | `eventTypeId`; confirmed records only |
| Ecommerce `onAfterOrderPaid` | `order_paid` | `revenue` in minor units (`subtotal - discount`), `currency` |
| School `onAfterEnroll` | `course_enrolled` | `courseId`; enrolled or completed records, including paid-hook retries |
| School `onAfterCourseComplete` | `course_completed` | `courseId`; completed records only |

Paths use static source paths (`/feature-flags`, `/forms`, `/newsletter`,
`/calendar`, `/store`, `/learn`), without request queries or tokens. No submission
fields, contact details, addresses, payment/cancellation credentials, flag payloads,
or targeting context are copied. Properties remain subject to Analytics' normal
size/type validation. These filters are not an anonymization service for custom
property values or application-defined flag keys.

Compose application hooks explicitly instead of replacing them:

```ts
hooks: {
  ...existingHooks,
  onAfterOrderPaid: async (order, context) => {
    await existingHooks.onAfterOrderPaid?.(order, context)
    await analyticsHooks.ecommerce.onAfterOrderPaid(order, context)
  },
}
```

Calendar still calls the legacy confirmation notification after rescheduling,
with optional `{ reason: "rescheduled" }` context. The Analytics helper ignores
that notification and emits only `booking_rescheduled`, so rescheduling does not
increase confirmation conversions.

Errors propagate to the source lifecycle. Existing verified-payment callbacks
can retry, so analytics event delivery can be repeated. These helpers do not add
exactly-once delivery or transactional outboxes. School's new completion observer
runs after the first committed transition, even when certificates are disabled;
it is not automatically retried and does not replace the certificate generator.

For a browser-observed lifecycle, use `createAnalyticsClientHooks` from
`@btst/plugin-analytics/client` with the same `createAnalyticsTracker()` instance
used for page views. Without an argument it uses the configured default tracker.
Browser events retain its in-memory session and DNT behavior; the bridge also
skips Global Privacy Control. Lifecycle callbacks pass the static source pathname
to the tracker, so a Calendar management URL does not add its bearer token to the
event path. `tracker.track(name, properties, path?)` accepts that optional pathname
without changing existing two-argument calls. Custom tracker implementations must
honor that path argument. This protection applies to the new
lifecycle bridge; general page-view/custom-event tracking still uses its existing
path behavior, so avoid collecting private bearer routes through those APIs. These observations are untrusted and cannot confirm
payment. Wire each event on one side to avoid counting both browser and server
callbacks.

When Analytics and any supported source are selected in `btst init`, Codegen
wires the corresponding server helpers. Its generated `session: () => null`
keeps collection disabled until you supply your application's consented session
resolver. Selecting either plugin alone adds no integration imports or hooks.
The tested CLI cohort includes Core 6.1, Analytics 1.1, School 2.0, Feature Flags 1.1,
Calendar 1.1, Ecommerce 1.0.1, and CMS 1.1 (required by School's revision-aware writes) for these APIs;
prepared package versions do not publish packages automatically.

## Page-scoped presentation

Set `overrides.analytics.pageOverrides.analyticsDashboard.TrafficChart` on `StackProvider` to replace the traffic chart without replacing date filters, metrics, tables, or CSV export. The component receives `AnalyticsTrafficChartProps` (`series`, the daily page view and visitor totals), exported from `@btst/plugin-analytics/client`.

```tsx
overrides={{
  analytics: {
    pageOverrides: {
      analyticsDashboard: { TrafficChart: ({ series }) => <MyTrafficChart series={series} /> },
    },
  },
}}
```

Unconfigured charts retain their built-in presentation. `analyticsDashboard` is the supported route key; `pageComponents.dashboard` still replaces the whole page. Reusable charts rendered outside the built-in dashboard do not inherit its page scope.
