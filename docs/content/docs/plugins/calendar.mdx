The Calendar plugin provides public booking pages and a host dashboard. Each
event type belongs to a host and defines its duration, location, capacity,
timezone, availability, and booking limits. Capacity `1` gives individual
appointments; a higher capacity lets several attendees book the same time slot.

Install `@btst/plugin-calendar@1.1.0` alongside `@btst/stack@6.0.0`.
Calendar has no dependency on other feature packages or `@btst/components`.
The canonical registration ID, permission namespace and database identities remain unchanged.

## Registration

Follow the [framework installation guide](/installation), then register both
halves with the canonical `calendar` key:

```ts title="lib/stack.ts"
import { createBackendStack } from "@btst/stack/api"
import { calendarBackendPlugin } from "@btst/plugin-calendar/api"

export const myStack = createBackendStack({
  basePath: "/api/data",
  plugins: { calendar: calendarBackendPlugin() },
  adapter,
  auth: serverAuth,
})
```

`adapter` is your configured BTST database adapter. Calendar writes require
transactions to be enabled in the adapter configuration; unsupported or disabled
transactions produce a `503 CALENDAR_TRANSACTIONS_REQUIRED` error. Configure
persistent adapters with isolated transactions so concurrent requests cannot
exceed capacity or limits. The memory adapter supports local development and
tests. Host writes are serialized through a host-row lock inside the transaction.

```tsx title="lib/stack-client.tsx"
import { createClientStack } from "@btst/stack/client"
import { calendarClientPlugin } from "@btst/plugin-calendar/client"

export function getStackClient(queryClient, origin: string) {
  return createClientStack({
    api: { baseURL: origin, basePath: "/api/data" },
    site: { baseURL: origin, basePath: "/pages" },
    queryClient,
    plugins: { calendar: calendarClientPlugin() },
  })
}
```

```css title="globals.css"
@import "@btst/plugin-calendar/css";
```

Mount the resolved client stack with `StackProvider` and the framework router
as described in the installation guide. Shared API, site, query client, and auth
services belong on the stack/provider, not in calendar overrides.

## Authorization

Register `calendarPermissions` from
`@btst/plugin-calendar/permissions` with your shared authorization
contract. Management operations require the authenticated host identity. Public
event reads, slot selection, and booking creation can allow guests; cancellation
requires the booking's secret token or the owning host.

The following rules assume an identity with a string `id` and show the Calendar
part of a `defineAuthorization` configuration:

```ts
permissions: [calendarPermissions] as const,
rules: ({ calendar }) => [
  calendar.eventType.list.when(({ identity, facts }) =>
    identity !== null && (!facts.hostId || identity.id === facts.hostId)),
  calendar.eventType.create.when(({ identity, facts }) =>
    identity !== null && (!facts.hostId || identity.id === facts.hostId)),
  calendar.eventType.read.when(({ identity, facts }) =>
    facts.public || identity?.id === facts.hostId),
  calendar.eventType.update.when(({ identity, facts }) =>
    identity?.id === facts.hostId),
  calendar.eventType.delete.when(({ identity, facts }) =>
    identity?.id === facts.hostId),
  calendar.availability.read.allow(),
  calendar.booking.create.allow(),
  calendar.booking.list.when(({ identity, facts }) =>
    identity !== null && (!facts.hostId || identity.id === facts.hostId)),
  calendar.booking.read.when(({ identity, facts }) =>
    facts.tokenValid || identity?.id === facts.hostId),
  calendar.booking.cancel.when(({ identity, facts }) =>
    facts.tokenValid || identity?.id === facts.hostId),
  calendar.booking.reschedule.when(({ facts }) => facts.tokenValid),
  calendar.booking.remind.when(({ identity, facts }) =>
    identity?.id === facts.hostId),
],
```

The backend derives `hostId` from the authenticated request identity for host
operations. Trusted server jobs may explicitly supply `hostId` when creating
event types or listing a host's records. Keep cancellation URLs private: anyone
holding the token can view, cancel, or reschedule that booking. Rescheduling uses
the same private `cancelToken`; a booking ID alone does not grant access.

## Availability and limits

- `duration` is an integer number of minutes, including custom durations.
- `timezone` is an IANA timezone such as `America/New_York`.
- `weeklyAvailability` contains `{ dayOfWeek, start, end }` rules. Sunday is
  `0`; times use `HH:mm` in the event type's timezone.
- `dateOverrides` contains `{ date, intervals }` entries. Each date replaces
  the weekly rules for that local date. An empty `intervals` array blocks the
  day; nonempty intervals add one-off availability.
- `capacity` limits attendees sharing a slot. Existing host appointments
  also prevent overlapping bookings across event types.
- `limits` accepts optional `perHour`, `perDay`, `perWeek`, and `total`
  positive counts per event type. Counts include each confirmed or pending-payment attendee
  reservation, using calendar periods in the host timezone; `total` counts
  all active reservations. Cancellations release availability and limits.

The public page interprets the selected date in the visitor's selected timezone
and displays slot times there. The backend validates the slot again on booking,
including availability, capacity, limits, and whether its start is in the future.

### External busy intervals

Pass an optional `getBusyIntervals(hostId, range)` callback in
`CalendarBackendConfig` (also exported as `CalendarBackendOptions`):

```ts
calendarBackendPlugin({
  getBusyIntervals: async (hostId, range) => {
    const events = await externalCalendar.listBusy(hostId, range)
    return events.map((event) => ({
      start: new Date(event.start),
      end: new Date(event.end),
    }))
  },
})
```

Both the requested range and returned intervals use absolute `Date` instants,
with exclusive ends. The range includes padding for viewer timezone offsets and
event duration; query all external events overlapping it. Any overlap blocks a
slot, including partial overlaps. Adjacent intervals do not block one another.
Booking and rescheduling fetch busy intervals again inside the host transaction.
Provider failures or invalid intervals reject the request rather than showing or
reserving unchecked times. Your integration owns credentials and provider access;
external calendar changes cannot be locked by the BTST database transaction.

### Prices and payment holds

Event types accept optional `price` and `currency` fields. Supply both or neither:
`price` is a nonnegative integer in minor currency units (`2500` means USD 25.00),
and `currency` is a three-letter uppercase currency code such as `USD`. Omit both
or set both to `null` to remove pricing. A zero price creates a free booking.
Existing databases need the two nullable columns on `calendarEventType`.

Positive prices create `pending_payment` bookings. These hold capacity, block
overlapping host events, and count toward booking limits just like confirmed
bookings. They can be rescheduled or cancelled using the private booking token.
Rescheduling preserves their payment status. Pending bookings do not fire
confirmation hooks or qualify for confirmed-booking reminders.

Configure an optional shared `PaymentAdapter` to create hosted checkout or a
client secret without installing Ecommerce:

```ts
import { stripeAdapter } from "@btst/stack/payments"

calendarBackendPlugin({
  paymentAdapter: stripeAdapter(stripeSecret, webhookSecret, {
    successUrl: "https://example.com/pages/calendar/book/consultation",
    cancelUrl: "https://example.com/pages/calendar/book/consultation",
  }),
})
```

Send signed provider events to `POST /calendar/webhook` under your API base
path, preserving the original raw request body. Bookings snapshot the amount,
currency and provider before checkout. Verified success changes `pending_payment`
to `confirmed`; failure or a full refund cancels the reservation and releases
capacity under the host lock. Retries validate the same payment reference and
cannot confirm a cancelled booking. Browser redirects never confirm payment.

The reservation response adds `checkout` with `redirectUrl` or `clientSecret`.
The UI opens hosted checkout; supply `overrides.calendar.renderPayment(checkout)`
on `StackProvider` for a provider SDK form using a client secret. The private
booking link can resume checkout via `POST /calendar/cancel/:token/checkout`,
and offers a payment status check. Hosted checkout saves the private token in
session storage before redirecting; returning to the public booking page restores
the management route. Hosted redirects require session storage. When it is unavailable, checkout
stays on the current page so the attendee can save the private link; enable
browser storage before retrying payment. Checkout initialization failure returns a
pending booking with `checkoutError`, preserving both the held slot and its
management token. Retry uses the same payment identity and caches a successfully
created checkout. Ordinary booking reads expose `hasCheckout`, and redact private
provider state and credentials.

Confirmation/cancellation hooks run after the payment transition and retry on
verified webhook re-delivery when they fail. Make them idempotent by booking ID;
external effects cannot be committed atomically with the database. Abandoned
holds still require application-owned cancellation; automatic expiry is not
included. Add a nullable private `payment` text column to `calendarBooking` in
your schema migration before enabling adapter payments.

Without `paymentAdapter`, existing host-managed paid holds remain supported.
After your own server verifies payment, call:

```ts
await myStack.trusted.calendar.confirmBookingPayment({ id: bookingId })
```

This operation has no HTTP route and rejects request-scoped calls. It cannot
confirm adapter-managed checkouts, which require their signed webhook. It fires
`onAfterConfirmBooking` once for the transition, and repeated calls are idempotent.

## Routes

With `site.basePath: "/pages"`, the client registers:

| Path | Purpose |
| --- | --- |
| `/pages/calendar` | Event types and upcoming/past booking dashboard |
| `/pages/calendar/events/new` | Create an event type |
| `/pages/calendar/events/:id/edit` | Edit availability, limits, and event details |
| `/pages/calendar/book/:slug` | Public booking page |
| `/pages/calendar/cancel/:token` | Booking details and cancellation |
| `/pages/calendar/reschedule/:token` | Choose a replacement time with the booking token |

API routes are relative to `api.basePath`, for example `/api/data`:

| Method | Path | Purpose |
| --- | --- | --- |
| GET, POST | `/calendar/events` | List or create host event types |
| GET, PATCH, DELETE | `/calendar/events/:id` | Read, update, or delete an event type |
| GET | `/calendar/book/:slug` | Read an active public event type |
| GET | `/calendar/book/:slug/slots?date=YYYY-MM-DD&timezone=UTC` | List available slots |
| POST | `/calendar/book/:slug` | Confirm a booking with `{ start, timezone, name, email }` |
| GET | `/calendar/bookings?period=upcoming` | List host bookings; also accepts `past` or `all` |
| POST | `/calendar/bookings/:id/cancel` | Cancel a booking as its owning host |
| GET, POST | `/calendar/cancel/:token` | Read or cancel a booking using its token |
| GET | `/calendar/reschedule/:token/slots?date=YYYY-MM-DD&timezone=UTC` | Available replacement times, excluding this booking's reservation |
| POST | `/calendar/reschedule/:token` | Move the booking using `{ start, timezone }` |

Slot responses contain `{ date, timezone, slots }`; each slot has UTC `start`
and `end` timestamps and a `remaining` capacity. A confirmed booking includes
its `cancelToken`. Show or deliver the cancellation link to the attendee. Host
dashboard responses omit the token value; hosts cancel through the protected
booking ID endpoint.

## Rescheduling and calendar invites

The confirmation links to booking management, where an attendee can reschedule
an upcoming active booking. A successful move keeps the booking ID and token and
releases the previous time. A failed move leaves the original booking intact.
The replacement is validated with the same host lock, external busy intervals,
timezone rules, group capacity and limits as a new booking. The existing booking
is excluded from those counts during replacement validation. Cancelled or past
bookings cannot be moved; deactivated event types offer no replacement times.

Confirmation, booking management, the host dashboard and reschedule confirmation
provide a **Download calendar invite (.ics)** link. The file uses UTC instants
(including across DST changes), a stable booking UID, escaped text and folded
UTF-8 lines following [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545).
Pending holds export as `TENTATIVE`; cancelled bookings export as `CANCELLED`.
Files contain no booking token. Downloads are manual snapshots, not calendar
subscriptions or automatic update notifications. Server applications can also
import `generateBookingInvite(booking)` from `@btst/plugin-calendar/api`; the
client entry is `@btst/plugin-calendar/client/hooks`.

## Lifecycle hooks and reminders

Pass hooks to `calendarBackendPlugin({ hooks })` to connect confirmation and
cancellation to your own email or notification service. `onAfterConfirmBooking`
receives the confirmed booking, and `onAfterCancelBooking` receives the cancelled
booking. Hooks run after the corresponding booking write.

`onAfterRescheduleBooking(booking, previous)` receives the committed replacement
and original booking. Confirmed moves also fire `onAfterConfirmBooking`; moving a
pending-payment hold only fires the reschedule hook. Repeating a move with the
same instants and timezone fires neither hook. Post-commit hook failures do not
undo the reservation, so delivery and retry handling belong to the application.

Calendar does not run a scheduler or deliver email. From your application-owned
scheduled job, call:

```ts
await myStack.trusted.calendar.remindBooking({ id: bookingId })
```

This invokes `onBeforeRemindBooking` and `onAfterRemindBooking` for a confirmed
upcoming booking. Your scheduler owns delivery timing and deduplication.

## Customization

Import calendar hooks from `@btst/plugin-calendar/client/hooks`, query
keys from `@btst/plugin-calendar/query-keys`, and page components from
`@btst/plugin-calendar/client/components`. Eject the page UI through the
`btst-calendar` shadcn registry item and pass replacement pages through the client
plugin's `pageComponents` option.

The plugin excludes round-robin assignment, automatic external calendar sync, payment processing,
video conferencing, recurring bookings, waitlists, and workflow automation.

## Confirmation notification context

Calendar 1.1 keeps both `onAfterRescheduleBooking` and the existing
`onAfterConfirmBooking` notification after moving a confirmed booking. The latter
receives an optional second argument `{ reason: "rescheduled" }`. Initial booking
and trusted payment confirmation keep their existing one-argument calls. Use
this context to avoid counting a reschedule as another initial confirmation,
while continuing to notify attendees of their new time.

### Affiliate payment attribution

Calendar 1.2 adds optional `hooks.capturePaymentAttribution({ request })` when an
adapter-backed paid booking is created. The private payment snapshot survives
checkout recovery. A verified paid `onAfterConfirmBooking` context includes
`payment: { amount, currency, attribution }` using the original booked price.
Free and host-managed confirmations omit payment context. Reschedule
notifications retain `reason: "rescheduled"` and create no new conversion. See
[Affiliate's conversion bridge](/docs/plugins/affiliate#verified-payment-conversion-bridges)
for optional commission recording without a Calendar dependency on Affiliate.

## Page-scoped presentation

Set `overrides.calendar.pageOverrides` on `StackProvider`. `calendarBooking` and `calendarReschedule` support `TimePicker`, which receives `CalendarTimePickerProps` exported from `@btst/plugin-calendar/client`: the selected date, timezone and start time, their change callbacks, slots query result, and optional capacity.

```tsx
overrides={{
  calendar: {
    pageOverrides: {
      calendarBooking: { TimePicker: MyBookingTimePicker },
    },
  },
}}
```

This customizes booking time selection while rescheduling retains the built-in picker. Custom pickers should clear the selected start when changing date or timezone and use the supplied slots and callbacks; booking submission, availability queries, and payment remain page-owned. Missing components use the built-in picker. `renderPayment` and whole-page replacements retain their existing behavior. Standalone pickers do not inherit page overrides.

The dashboard, event editors, and cancellation page do not select a time and have no `TimePicker` slot.
